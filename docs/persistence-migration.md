# Phase 1 → Phase 2 JSON migration

**P2 update:** [P2 mapping and DXF contract](p2-dxf.md) supersedes historical P1 statements about optional horizon elevations, mandatory per-point coordinate strings, absent plans and schema 1. P2 adds nominal Z provenance and immutable managed DXF revisions on the same graph; orientation/measurement conventions are unchanged.

## Deployed compatibility contract

Bundle identifier remains **`com.tinuvael.FieldForge`**. Do not uninstall the app or change its signing identity/bundle identifier to test an upgrade. Device records were not accessed by this work.

Application Support/FieldForge/**`measurements-v1.json`** remains the active path; its filename is retained for deployed compatibility even when its envelope is schema **2**. Phase 1 is `{schemaVersion: 1, measurements: [...]}` using Swift `JSONEncoder` default dates (seconds since 2001-01-01 UTC), UUID strings, full orientation/status/normal, reference, quality, required `SensorSample`, notes, plane and algorithm version. Phase 2 keeps these fields, makes diagnostics source-dependent, and requires `source` and `directionMeaning`, with optional `manualInput`. Dates are not reinterpreted as Unix seconds. CSV timestamps use ISO 8601 UTC instead.

## Load and commit sequence

1. Read bytes; decode the header before payload. Unknown/missing versions or malformed JSON fail explicitly. No fallback to an empty journal.
2. Version 1 uses a separate strict legacy DTO with a **required** sample. Add `iPhoneSensor` for `coreMotion`, `simulatorMock` for mocks; derive only direction meaning from presence/absence of the stored direction. Preserve all original fields without recalculating/replacing them.
3. Validate each migrated record with unchanged sensor processing rules: diagnostics, timestamp equality, quality, orientation, reference, plane and algorithm. Reject duplicate UUIDs. Invalid records are not skipped silently.
4. Encode schema 2 and check complete value equality after decoding. This happens before any change to the active file.
5. Copy the original to **`measurements-v1.json.phase1-backup`** without overwriting an existing backup. Verify exact byte equality. An identical backup permits retry; a conflicting or partial backup stops migration and requires recovery. A copy failure leaves the active file intact.
6. Recheck the active bytes, then replace the active file using Foundation's atomic write. Only after success is loading marked successful and writing enabled. The original bytes remain in the backup after migration. On a write failure the original active file remains intact under atomic replacement semantics.

Version 2 is validated and read without migration or rewriting. A schema-2 sensor record cannot omit its sample; a manual record cannot contain a sample or masquerade as sensor data. Manual values must match their original validated inputs, north, convention and quality. External-instrument ingestion is reserved but unsupported.

## Failure and subsequent writes

Any load/migration error disables writes both in the store and in `AppModel`; saving directly without calling `load()` first still performs a protected load. The original file is never deleted/reset to “fix” an error. Valid saves/deletions use schema 2 and atomic replacement after validation. A byte comparison against the last loaded/saved file detects intervening changes and refuses to overwrite them. This is a single-process guard, not a general cross-process transactional database lock.

The backup is immutable during normal operations, even journal deletion. Do not automatically restore it if schema 2 later becomes corrupt: that could discard newer manual observations. For recovery, copy the active file and backup out first, inspect/repair a staging copy, validate, then explicitly choose a restored journal. A partial/conflicting backup may be renamed only after preserving it and verifying the active original. Storage-full and device power-loss behavior still require platform testing; no durability stronger than Foundation atomic write is claimed.

Phase 1 cannot read schema 2. Downgrading requires an explicit recovery/export plan; restoring the Phase 1 backup loses observations captured since upgrade. App removal still removes sandbox data. CSV is not a full-fidelity backup of sensor vectors/uptime; a structured JSON + attachment backup service is planned, not yet exposed in the UI.

## P3.1 mapping schema 3

The independent measurement schema above is unchanged. The mapping aggregate at `mapping-v1.json` now adds an original-measurement table with exactly-one-point ownership through UUID references. The existing backup/validated round-trip/atomic upgrade sequence preserves old schema-1 bytes in `.p1-backup` and schema-2 bytes in `.p2-backup`, retaining observations and managed DXF references unchanged. Failed/unsupported/corrupt loads block writes, never reset. Schema 3 requires the evidence table even when empty. See [P3.1 contract](p3-measurements.md).

## P3.2b mapping schema 5

The existing mapping path stays `mapping-v1.json`; independent measurement files are unchanged. Schema 5 adds optional point-level Q/RMR89 assessment snapshots. Valid schema 1–4 graphs migrate through the existing exact-byte non-overwriting `pN-backup`, round-trip and source-change checks, then atomic replacement. Missing historical assessments stay nil. Saved Q method/result/input consistency is validated and unknown method versions fail closed. An incomplete Q record retains its missing list; RMR89 has no numerical result. Append-only observations protect assessments together with geology and source readings. Failure never creates an empty replacement journal. See [P3.2b methodology/storage contract](p3-2b-ratings.md).

## P3.3 mapping schema 6

`mapping-v1.json` adds a required `revisions` array, empty on upgrade. Schemas 1–5 follow the same validate → encode/round-trip → exact non-overwriting `.pN-backup` → source recheck → atomic replacement sequence. Schema 5 produces `.p5-backup`; observations, assessments, geology, plan references and measurements are preserved. Current schema 6 must contain the revisions table; omission, broken predecessor chains, inconsistent ownership or invalid snapshots fail closed. The store refuses removal or modification of every previously persisted revision, original observation, original measurement and plan reference. It still keeps `.previous` for each successful commit. Old application versions cannot read schema 6. Preserve the entire journal and original `plans/` directory before recovery; do not reset or automatically roll back to a migration backup. A nonempty revision table under an old schema header is rejected before any migration/backup write; history is never silently discarded because a header was damaged. See [revision contract and limitations](p3-3-revisions.md).
