# Stage 4b · Excel Exchange round trip

The iPhone journal can apply selected edits from a FieldForge Exchange workbook. It uses the existing `FieldForge-Exchange/1` worksheets, identifiers and schema-8 journal. The [v1 format reference](excel-exchange-v1.md) describes the exact sheet layouts and source records. This document defines the current editing policy.

## Field workflow

1. In **Журнал → Выгрузка**, export **Excel Exchange · обмен** for the project and date range. Work in a copy of the XLSX.
2. In Excel, follow **Колонки**. Keep the data cells formatted as Text and sort entire rows. For an existing observation edit supported inputs and enter a `correction_reason`. You can also supply `correction_author`.
3. On iPhone, open **Журнал → Импорт Excel** and choose the workbook in Files. The preview shows the number of physical observation rows, plus new, updated, unchanged, duplicate, conflicting, invalid and unsupported records. Child-sheet diagnostics identify their sheet and row or column when available. Open a row to review the values from export and the proposal, then select the rows to accept. Leave valid rows unselected to skip them. Conflicting rows cannot be accepted. Choose **Сохранить решение об отклонении** to record the decision when confirming. If a local revision conflicts, re-export before proposing another change.
4. Confirm the selection and review the report. If an earlier import was interrupted, choose the same saved file and explicitly continue or reject any pending rows. Re-export from the journal to see the effective values and revision history.

For existing editable cells, a blank preserves the exported value. Enter `#CLEAR` to clear a supported optional value or text. If the exported value is already the literal `#CLEAR`, use `#CLEAR!` to clear it. For an interval boundary, clear both the text and metre cells. Empty cells in a new row have their usual missing-value meaning. A missing row never means deletion. A duplicate with identical values is reported and collapsed to one logical row. Divergent duplicates block the ambiguous observation, including UUIDs that differ only in letter case.

## Editable fields

| Sheet | Stage 4b input | Validation and provenance |
| --- | --- | --- |
| `points` | `notes`, `rock_json` with `code` and optional `name`, `position`, interval start/end text and metres, `has_geology` for adding an empty geological context or entering interval/position, correction reason and optional author | Keep rock codes as text, including leading zeroes. Match interval text and metres under the stored picket convention. Existing geological context cannot be removed. |
| `joint_sets` | Existing J1–J4 `persistence_m`, `aperture_mm`, `roughness`, `infill`, `notes`. `spacing_m` when the saved spacing has explicit manual provenance | Spacing is positive, persistence and aperture are nonnegative. A changed joint set receives a new interpretation revision within the observation revision. Its source orientation, author, method, evidence links and spacing provenance stay attached. Estimated or legacy spacing and all J5 fields are read-only. |
| `tectonic_structures` | Existing `type`, `thickness_m`, `position`, `description` | Types are `fault`, `shearZone`, `fractureZone`, `other`. Thickness is nonnegative. Source orientation and structure picket stay attached. |
| `assessments`, Barton Q | `rqd_text` and the five coefficient text columns. To change a coefficient category or selection origin, edit the corresponding `input_json` object as well and keep the text value in agreement | The existing NGI 2025 method identifier selects the existing evaluator. Method, source, assessor, evidence, adjustment settings and assessment time stay attached. Category, contact and coefficient checks come from the saved method. A coefficient with recorded evidence can only be edited within its existing category. |
| `assessments`, RMR89 | For `Bieniawski-RMR89/table-4.1-categories-v4`, edit `rqd_text` and `rmr_spacing_m_text`. To change their bands, edit `basicSelections.rqd` and `basicSelections.spacing` in `input_json` | The existing v4 evaluator checks the supplied inputs and explicitly selected bands. Clearing a number leaves its explicit band in place until the corresponding selection is removed in JSON. Other inputs and source information stay attached. Legacy, input-only and pre-v4 assessments are read-only. |
| `assessments`, categorical GSI | `input_json.lower` and `input_json.upper` | Supply an explicit interval within 0–100 that contains the saved final value, if present. The saved category, final value, timestamp and method stay attached. Chart-based GSI is read-only. |
| `points`, new rows | `record_action=new`, unique `client_record_id`, explicit existing project/horizon/excavation IDs, picket and chainage convention, time and offset, field descriptions, interval and optional manual location | Keep original/version/fingerprint fields, creation/correction metadata and measurement references empty. Keep `point_id` empty. The approved client UUID becomes the point UUID, and confirmation supplies creation time. Add assessments, joint sets, tectonic structures, measurements and photos for new points in the app. |

The original observation and every previously saved assessment snapshot remain in the journal. The accepted inputs and any resulting Q or RMR89 evaluation live in the new observation revision. When a duplicated assessment input is edited in both the text column and JSON, the two must agree. JSON does not permit additional keys or edits to protected properties.

Every unlisted field is read-only. This includes existing point locations, capture times, chainage, coordinate and DXF provenance, raw compass and manual measurements, assessment outputs and method identifiers, historical J5, photograph files and metadata, project lists, and the entire `source_records` sheet. RMR76 and JCond76 are preserved as saved. The Exchange v1 workbook carries regulatory categories in protected source records and has no editable projection for them. Stage 4c owns Regulatory `Data!A:AD` import. The existing regulatory export is unchanged.

## Commit and recovery

- The reader validates the required sheet names and column keys, original source records, and workbook metadata. New exports add a metadata checksum while retaining the v1 sheet layout. The importer also accepts the original v1 guide and metadata without that checksum. A checksum detects changed bytes and does not authenticate workbook authorship.
- Confirmation reads the selected file again and requires the same bytes as the preview. Each approved operation has a stable ID derived from the workbook UUID, exact file fingerprint, source row identity and decision. A completed operation is recognized when the same file is reselected, including after app restart. Re-saving the file creates a different source version. The observation baseline or new-point UUID binding still prevents duplicate mutations.
- Each row commits independently through the Stage 4a storage owner. Before writing a mutation, it rechecks the observation revision, snapshot and export graph, including parent/plan context, against the latest journal. The observation or revision and applied receipt are saved atomically. When saving fails, earlier committed rows remain, a persisted intent is shown as pending, and rows that were never reached are shown separately. Recovery requires the original approved XLSX bytes and reuses the intent's assigned timestamps.
- Changes to protected shared sheets or mismatched immutable evidence block the workbook. A row-specific error blocks the affected row. A skipped valid row can be selected at a later confirmation if its baseline is still current. Conflicts never overwrite journal changes.
- The workbook contains photo and plan metadata. Original files remain in managed storage and in full offline backups. Excel Exchange is a scoped exchange mechanism.

The reader accepts text in inline or shared strings and ZIP STORE or DEFLATE. It also accepts bounded Office workbook save metadata, including local AutoFilter ranges and calculation-engine feature markers. Formula cells, external references, macros, added/renamed worksheets and pasted Excel numbers or dates are rejected.
